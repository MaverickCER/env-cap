# Generated artifacts: what `env-cap` produces, and what it deliberately doesn't

Check this page before assuming `env-cap` generates something it doesn't. It
is the canonical place for that check, for a human or an AI agent working in
this repository or a consuming project.

Every artifact below is produced by `generateEnvArtifacts()`. Nothing here is
generated by a separate, independently-derived pipeline. The `env-cap` CLI is
a thin wrapper for the manifest/evidence outputs only (see
[ADR 0046](decisions/0046-cli-restricted-to-runtime-and-evidence-output.md)).
The documentation catalog, `.env.example`, and the ownership report have no
CLI flag at all, only a direct `generateDocumentation()`/`generateUsageReport()`
call.

Concretely, `computeArtifacts` (the function both `generateEnvArtifacts` and
`checkArtifacts` share) runs one `assembleProject()` parse/link pass. It then
builds all seven canonical fact models (ADR 0024) from that single result.
Every artifact in this file is a projection of that same run's models, not a
second, independently-assembled source. `--evidence <path>` writes the
composed Evidence Model to disk directly, as JSON. That serves a project that
wants the canonical artifact itself rather than only its Markdown projections.

**Every artifact in this table is evidence that can _support_ a review
process, never a compliance claim**. Such a process might be a security
review, a privacy review, or a platform audit. Static analysis of one repository cannot, by itself,
establish compliance with any external standard. Every rendered artifact
that carries this claim opens with the same disclaimer
(`evidenceDisclaimer()` in `generated-banner.ts`, byte-identical to
data-cap's own):

> Machine-generated engineering artifact assembled from statically-provable
> code facts and author-declared documentation. It can support a security,
> privacy, or compliance review. It does not itself establish compliance
> with any standard.

## Declared vs. proven vs. evidence

Every fact in every generated artifact is one of exactly three kinds. A
rendering function may never blend them or imply one is another:

- **Declared**: metadata the author wrote via `documentEnv()`'s
  `VariableDocs`/`ContractDocs`. The fields are `description`, `owner`,
  `sensitivity`, `expiresAt`, `refreshInstructions`, `setupInstructions`,
  `required`, `deprecated`/`deprecatedReason`/`removeBy`, `renamedFrom`,
  `purpose`, `legalBasis`, `retention`, `dataResidency`, `auditRequired`,
  `metadata`. Presence is checked; correctness, adequacy, and enforcement are
  never claimed. A report may say a variable's retention policy is
  _"documented,"_ never that it is _"sufficient"_ or _"enforced."_
- **Proven**: facts derived by AST analysis of the actual source. They cover:
  - whether a declared variable is actually read anywhere in the scanned
    surface (`UNCONSUMED_OWNED_VARIABLE`);
  - which files import/reference a given contract (Dependency Model);
  - every exclusive-group/compatibility conflict between contracts
    (`FindingCode`'s compatibility family).

  These are statically provable from the code that exists today, in this
  repository, at analysis time.

- **A third case, named explicitly because it's neither**:
  `VariableDocs.evidence.dynamicAccess`. It uses an ADR 0053-equivalent
  citation mechanism, mirroring data-cap's identical design. It is declared,
  like every other governance field. Unlike every other one, it's re-verified
  every run against a persisted content hash of the cited file
  (`MISSING_DYNAMIC_ACCESS_CITATION`/`STALE_DYNAMIC_ACCESS_CITATION`). A
  passing check establishes only that the citation is currently _supported
  by its own citation/integrity state_. That means the cited file exists and
  hasn't visibly changed since the developer wrote it. It never means the
  described access has been proven to happen there. No rendering of this
  field ever uses "verified" or "proven" language for this reason.

## Built in this release

| Artifact                                                                                    | Generator                                      | What it answers                                                                                                                                                                                                                                                                                                   |
| ------------------------------------------------------------------------------------------- | ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Manifest** (`--location`)                                                                 | `generateEnvManifest` (Contract Model)         | A single, deterministic `.ts` file re-exporting every _active_ contract, projected from the Contract Model (not a second source of truth). `runtime/validate.ts` validates real `process.env` values against exactly this manifest.                                                                               |
| **Documentation catalog** (`generateDocumentation()`, no CLI flag, ADR 0046)                | `generateDocumentation`                        | Per-contract variables: `description` ("why") and `owner`/`sensitivity`/`purpose`/`legalBasis`/`retention`/`dataResidency` (labeled declared, not verified). It also has a live "expiring soon or already expired" section sourced from the Lifecycle Model.                                                      |
| **`.env.example`** (`generateDocumentation()`'s `envExample` option, no CLI flag, ADR 0046) | `generateDocumentation`                        | One line per active variable, generated from the same declared metadata the documentation catalog renders. It is never hand-maintained, and never a second copy of the schema to drift from the real one.                                                                                                         |
| **Dependency & Ownership report** (`generateUsageReport()`, no CLI flag, ADR 0046)          | `generateUsage` (Dependency + Ownership Model) | The owner → variables matrix, plus a real, in-repo, AST-proven consumer graph: which files actually read which variable, never guessed at. `UNCONSUMED_OWNED_VARIABLE`/`ABANDONED_CONTRACT` are warnings; `UNRESOLVED_CONSUMER`/`INDETERMINATE_OWNERSHIP` stay info, escalated only by `--strict-ownership`.      |
| **Evidence Model** (`--evidence`, ADR 0038)                                                 | `generateEvidenceModel`                        | The composed `EvidenceModel` (ADR 0024's seventh model) as JSON, plus a paired `.fingerprint` sidecar, holding whichever Contract/Dependency/Ownership/Finding/Lifecycle/Change models were computed this run. It is always composed in memory; the flag only controls whether it's additionally written to disk. |
| **JSON report** (`--json`)                                                                  | CLI (`src/cli/json.ts`)                        | The full result as one versioned envelope (`@maverickcer/env-cap/schema`): every finding, every generator's output, and the composed Evidence Model. A CI step or another tool can consume it without parsing human-readable text.                                                                                |
| **Drift check** (`--check`)                                                                 | `checkArtifacts`                               | Recomputes every requested artifact and diffs it against disk; it writes nothing and exits non-zero if anything is stale or missing. Its exit code reflects staleness only, independent of `--strict*` finding severity.                                                                                          |
| **SARIF log**                                                                               | `buildSarifLog` (library export)               | A SARIF 2.1.0 adapter over the Finding Model, for a security-tooling pipeline that already ingests SARIF. It is not CLI-wired. Whichever project needs it calls it directly, as an ordinary consumer of the public Finding Model type (the same boundary Phase 4/5's own generator scripts sit behind).           |

## Canonical fact models (ADR 0024)

Seven canonical, versioned, JSON-serializable models form the
machine-readable surface that every rendered artifact above is a projection
of. `defineEvidenceProjection()` consumers (below) read them instead of
re-deriving facts from raw source.

| Model            | Builder                 | What it answers                                                                                                                                                                                                                                                                                               |
| ---------------- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Contract Model   | `buildContractModel`    | Every discovered contract (active or not) and its variables: the schema shape itself, projected and sorted deterministically.                                                                                                                                                                                 |
| Dependency Model | `buildDependencyModel`  | Every proven consumer relationship, indexed by contract/variable and by consuming file. It is the fact the ownership report projects, computed once.                                                                                                                                                          |
| Ownership Model  | `buildOwnershipModel`   | Every contract and variable's effective owner, plus first-class `unownedContracts`/`unownedVariables` arrays.                                                                                                                                                                                                 |
| Finding Model    | `buildFindingModel`     | Every rule violation and derived risk signal, unified behind one shape with a stable `code` and a structured `EvidenceReference`. The SARIF adapter and Evidence Model compose from it.                                                                                                                       |
| Lifecycle Model  | `buildLifecycleModel`   | Every contract and variable's lifecycle data: expiry, deprecation, rename correlation.                                                                                                                                                                                                                        |
| Change Model     | `buildChangeModel`      | What changed since the last persisted evidence snapshot: the manifest diff, keyed for a "changes since last report" section.                                                                                                                                                                                  |
| Evidence Model   | `generateEvidenceModel` | The composition of the other six into one artifact, which every reference projection below reads. Two of the seven are separately published as JSON Schema (`@maverickcer/env-cap/schema`, `@maverickcer/env-cap/schema/contract-model`); the rest are TypeScript-typed only, not yet independently schema'd. |

A first wave of reference projections ships alongside the models themselves:

- `configurationReference`, `ownershipSummary`, and `expiringSoonReport`, all
  built through `defineEvidenceProjection()`;
- `buildSarifLog`, a SARIF 2.1.0 adapter over Finding Model.

Every one of these is an ordinary consumer of the public model types above.
None has a privileged internal path a downstream tool couldn't also use. A
future open-standard projection would be architecturally no different. It
would be another `defineEvidenceProjection()` consumer, not a bespoke script
bypassing this model.
