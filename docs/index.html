Configuration, owned

Every environment variable has an owner, a reason to exist, and a lifecycle you can query.

env-cap treats configuration the way applications already treat their APIs, data models, and dependencies — not as loose strings read off process.env, but as a capability-owned contract.

You replace nothing. env-cap sits next to your existing validation — Zod, envalid, t3-env, plain dotenv — or with none at all.

Quick start 
npm install env-cap
          npx env-cap init

Why it exists

Secret managers and validators answer different questions.

A secret manager decides where a value lives. A validator decides whether a value is well-formed. Neither one answers:

  • Why does this variable exist, and which capability actually depends on it?
  • Who owns it, and who do you page when it needs to rotate?
  • Is it still needed, or is it a leftover from a feature that shipped and moved on?

The cost of not answering them

As an application grows past a handful of variables, those questions end up answered nowhere executable — a wiki page, a Slack thread, someone's memory. env-cap makes the answer part of the code: each capability declares the environment it owns, and a build-time pass turns every declaration into a project-wide ownership and lifecycle view.

How it works

Runtime and build-time stay separate on purpose.

Runtime receives only what the application requires — zero dependencies, no filesystem access. Build tooling creates the visibility needed to understand and maintain dependencies, as an explicit development or CI step, never at startup.

A capability's schema file branches into a runtime path for validated application access and a build path for generated documentation and visibility artifacts.

  1. Capability schema file
    1. Runtime path
      1. createEnv()
      2. validateEnv()
      3. Typed, capability-scoped access
    2. Build path
      1. documentEnv()
      2. Static AST analysis — never imported or executed
      3. Generated manifest, docs, ownership report

The build package parses schema files as TypeScript ASTs and never imports or executes them — a static-analysis boundary that prevents unfamiliar code from running as a side effect of generating documentation, manifests, and dependency insight.

Why not just dotenv, Zod, envalid, or t3-env?

You keep all of them.

env-cap doesn't replace your loader or your validator — it adds the layer none of them cover.

Where common approaches stop and env-cap begins
Tool What it solves What it doesn't
dotenv Loads values from a .env file into process.env Says nothing about who owns a value, whether it's still used, or when it expires
Zod / envalid / t3-env Validates that a value has the right shape Same gap — a well-typed variable can still be an orphaned, unowned, or expired one
A secret manager Decides where a value physically lives and how it's rotated Says nothing about which capability in your code actually depends on it

Plug an existing Validator<T>/Processor<T> function straight into a contract, or use env-cap's own lightweight helpers when a validation library is more than the variable needs. What env-cap adds is ownership, lifecycle, and a static-analysis pass that can tell you a capability declares owning a variable nothing actually reads.

Not "CI failed" — a rotation deadline that already passed, and two variables a capability declares owning but nothing in the codebase actually reads. Both are real, provable facts about this fixture, not synthetic examples.

Adoption

From one schema to capability-owned contracts.

Most applications start with a single, centralized schema — and that's a fine place to stay if it's working. As ownership boundaries start to matter, contracts move closer to the capability that consumes them, with no change to the runtime model.

You probably don't need it when

Your application is small, one team owns every configuration decision, environment variables are few and stable, and you already have enough visibility into your dependencies. A validation library alone, or plain dotenv, may be all you need.
