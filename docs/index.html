    Configuration is an application contract.

    APIs define how systems communicate. Data models define how information is structured. Dependencies define what an application relies on to function. Configuration is another contract: it describes the external requirements needed for the application to operate.

    env-cap makes configuration requirements explicit as part of the application definition while leaving sensitive values and deployment-specific concerns in the systems designed to manage them.

    • Discover application dependencies.
    • Preserve configuration knowledge.
    • Coordinate configuration changes.
    Get Started Read the Architecture

    The problem

    Configuration becomes harder to understand as applications grow

    Environment variables start as simple configuration values, but over time they become critical application dependencies without the context needed to safely manage them.

    • Variables exist without clear ownership or purpose.
    • Removed features leave unused secrets and configuration behind.
    • Teams cannot easily identify which capabilities depend on a variable.
    • Documentation drifts because it lives separately from the code that requires it.
    • Security context is lost because rotation and lifecycle expectations are not tracked.
    • Configuration changes become risky because dependency impact is unclear.

    Cost of the status quo

    Without application-aware configuration visibility, teams accumulate unknown dependencies, stale variables, undocumented requirements, and operational uncertainty. Configuration remains available, but understanding why it exists becomes increasingly difficult.

    Configuration visibility

    Configuration values are not the same as configuration understanding

    Existing tools are excellent at storing, loading, and validating configuration. env-cap adds the missing application context: why dependencies exist, who relies on them, and how they should be maintained over time.

    Works with existing tools

    env-cap is not a replacement for secret managers, dotenv, or validation libraries. It adds the application context needed to understand and maintain configuration as systems grow.

    The solution

    Define configuration as part of the application

    An environment variable is more than a value. It represents a dependency between an application capability and the systems it relies on. env-cap lets each capability declare its configuration requirements, ownership, and lifecycle information alongside the code that uses them, while build-time tooling creates a complete view of those dependencies.

    features/payments/env.schema.ts 
    export const paymentsEnv = createEnv({
  STRIPE_KEY: {
    validator: all(string(), minLength(1)), // using whatever validation library you prefer
  },
});

export const paymentsDoc = documentEnv({
  STRIPE_KEY: {
    description:
      "Payment provider authentication key required by payment processing capability. To rotate this key, reach out to the payments team to have them rotate the STRIPE_KEY for Stripe.",
    expiresAt: "2026-12-31",
  },
});

paymentsEnv.STRIPE_KEY;

// Build artifacts reveal:
// - who requires this variable
// - why it exists
// - how it should be maintained

    Runtime access remains local and type-safe, while build artifacts bring configuration context together across the application to make dependencies, ownership, and lifecycle information easier to understand.

    Configuration stays with the application. Understanding scales across the system.

    Why configuration context matters

    Configuration should explain itself

    Environment variables are not just values. They are application dependencies with owners, purposes, and lifecycles. As systems grow, keeping that context connected to the code that depends on it becomes increasingly important.

    • Dependencies should have clear ownership.

      The teams responsible for application behavior should understand the configuration required to support that behavior. env-cap keeps dependency context close to the capabilities that consume it while still providing a complete application view.

    • Removing capabilities should remove configuration burden.

      Configuration often survives longer than the features that required it. Ownership metadata makes unused variables easier to identify and remove instead of allowing forgotten dependencies to accumulate.

    • Configuration changes should be visible during review.

      When a capability changes its dependencies, those changes should be reviewed alongside the code that introduced them. This keeps configuration decisions connected to application changes instead of hidden in separate documentation.

    • Reusable packages should declare their own requirements.

      Internal libraries and installable capabilities can provide their own environment contracts without requiring every application to manually copy and maintain configuration definitions.

    • Configuration lifecycle should follow application lifecycle.

      Rotation schedules, ownership details, and operational notes remain attached to the dependency definition instead of becoming separate documentation that can drift over time.

    How it works

    Runtime and build-time stay separate on purpose

    env-cap separates application execution from configuration intelligence. Runtime receives only what the application requires, while build tooling creates the visibility needed to understand and maintain dependencies.

    A capability's schema file branches into a runtime path for validated application access and a build path for generated documentation and visibility artifacts.

    1. Capability schema file
      1. Runtime path
        1. createEnv()
        2. validateEnv()
        3. Typed application access
      2. Build path
        1. documentEnv()
        2. Static analysis (AST parsing — never imported or executed)
        3. Generated visibility artifacts

    Runtime stays modular and contains only what the running application requires. It has zero runtime dependencies and no filesystem access. Build tooling provides application-wide visibility as an explicit development or CI step rather than during startup.

    The build package parses schema files as TypeScript ASTs and never imports or executes them. This creates a static-analysis boundary that prevents unfamiliar code from running as a side effect while generating documentation, manifests, and dependency insights.

    FAQ

    Common architecture questions

    Why does configuration need more context than validation provides?

    Validation answers whether an application has acceptable configuration values. It does not explain why those values exist, which capabilities depend on them, how they should be maintained, or whether they are still needed.

    env-cap adds application context around configuration dependencies so teams can understand the relationship between their code and the environment variables required to run it.

    How does env-cap know which configuration is required?

    Required configuration is determined during build time. env-cap discovers environment contracts from the application and its dependencies, including reusable packages installed through node_modules. This allows internal libraries and shared capabilities to declare their own requirements without requiring applications to manually copy or pass configuration definitions around.

    env-cap generates a central manifest containing the active environment contracts required by the application. At startup, validateEnv() uses that manifest to quickly validate the complete environment before the application serves traffic.

    What happens when capabilities define conflicting requirements?

    env-cap surfaces conflicting definitions during build-time artifact generation. This allows teams to determine whether similar requirements represent the same dependency, need to be synchronized, or should remain separate because they represent different resources.

    What happens when two capabilities use the same variable name differently?

    Identical variable names do not automatically represent identical dependencies. Each capability defines how a variable is obtained, validated, and used. Generated artifacts make these relationships visible so teams can decide whether capabilities should share a configuration value or use separate resources.

    Runtime validation can detect incompatibilities based on how a variable is used, not only whether the value exists. This helps identify cases where configuration appears valid but does not satisfy the capability that consumes it.

    Why is adding configuration context worth the additional structure?

    Environment variables are easy to create but difficult to maintain when their purpose, ownership, and lifecycle become unclear. env-cap connects configuration requirements to the application context needed to operate them safely.

    • Developers understand why each variable exists, where it is used, and which capabilities depend on it.
    • New contributors can discover requirements from the code that consumes them instead of searching through outdated documentation or historical pull requests.
    • Teams can identify unused, undocumented, or orphaned configuration that accumulates after features change or are removed.
    • Operations teams gain visibility into configuration dependencies, ownership, and lifecycle information before changes become incidents.
    • Security teams gain additional context around sensitive configuration, including the capabilities that require access and expected lifecycle management.
    • Teams can reason about configuration changes as application dependency changes instead of treating environment variables as unrelated key-value pairs.
    Do I need to reorganize my application to adopt env-cap?

    No. env-cap does not require replacing centralized configuration approaches. Teams can keep existing schemas, loaders, and validation patterns while adding contracts to gain improved visibility, documentation, and lifecycle information.

    Capability ownership is an adoption pattern for teams that want configuration requirements to live closer to the code that consumes them. Teams can introduce ownership boundaries incrementally where they provide value.

    How does env-cap handle sensitive configuration?

    env-cap does not store, fetch, transmit, or manage secrets. Secret storage remains the responsibility of your deployment environment or secret manager.

    env-cap provides context around configuration dependencies while keeping sensitive values out of generated artifacts. Documentation metadata should describe requirements, ownership, and lifecycle information, never credentials.

    For complete security boundaries and threat considerations, see SECURITY.md .

    Does env-cap execute application code during analysis?

    No. Build-time analysis parses schema files as TypeScript ASTs and never imports or executes them. This prevents unexpected code execution while generating documentation and manifests.

    Does env-cap add runtime overhead?

    Yes. Like any configuration validation system, env-cap performs work during initialization. The difference is that the cost is bounded and predictable.

    Environment setup and validation scale linearly with the number of configured variables:

    • Creating the environment interface: O(N)
    • Running initial validation: O(N)

    After initialization:

    • Reading environment values: O(1)
    • Re-validating: O(1) because validation results are cached

    This design keeps configuration safety checks at startup instead of repeatedly adding processing overhead throughout application execution.

    For enterprise-scale configurations, env-cap benchmarks initialization against thousands of variables to detect performance regressions.

    For complete performance characteristics powered by real benchmarks, see PERFORMANCE.md .
