# Secrets-rotation compliance log generator

Generates `docs/SECRETS-ROTATION-LOG.md` -- a NIST SP 800-53 Rev. 5 **IA-5** (Authenticator
Management) rotation-compliance document, built from `env-cap`'s own schema-level lifecycle
fields: the pre-existing `expiresAt`/`refreshInstructions` (already used by `../generate-docs`'s
ENVIRONMENT.md and the lifecycle report), plus `authenticatorType`/`rotationPeriod`/
`lastRotatedAt`/`rotationTriggerEvents` and a computed `rotationStatus` per variable
(`compliant`/`overdue`/`expired`/`undeclared`) -- see `src/build/lifecycle-model.ts` in the main
package for exactly how that status is derived, and its own doc comment for the interpretive
judgment call involved.

Peer to [`../generate-docs`](../generate-docs) -- same directory-per-generator convention that
example established (C5), just for a different document.

## Architecture

- [`types.ts`](types.ts) -- `RotationLogEntry`/`RotationLogModel`, this document's own JSON shape.
- [`build-model.ts`](build-model.ts) -- the real seam: a pure function, `EvidenceModel ->
  RotationLogModel`. An org that wants the computed values directly (to feed its own dashboard, a
  different renderer, a CI gate) calls `buildRotationLogModel()` on any `EvidenceModel` it already
  has, without touching `render.ts` at all.
- [`render.ts`](render.ts) -- the default Markdown renderer. There is no single official
  NIST-published template for an IA-5 rotation log -- the control states the requirement (a
  time-based rotation period per authenticator type, plus event-based refresh triggers), never a
  reporting format -- so this file's exact column layout is a documented judgment call, not a
  reproduction of a NIST-provided shape. Only IA-5's main statement is implemented; IA-5(13)
  ("Expiration of Cached Authenticators," a distinct control about cached credential copies, not
  primary-authenticator rotation) is not, and the rendered document says so rather than citing a
  control it doesn't actually speak to.
- [`print-lines.ts`](print-lines.ts) -- `printJsonLines()`, a shared line-by-line JSON printer
  `run.ts` uses to demonstrate the `build-model.ts` escape hatch on the console, not just document
  it.
- [`run.ts`](run.ts) -- wires it together: reads `docs/env.evidence.json` via `@maverickcer/env-cap/build`'s
  `getEvidenceModel()`, builds the model, writes `docs/SECRETS-ROTATION-LOG.md`, and prints the raw
  model via `printJsonLines()`.

## Why this reads evidence.json instead of re-running discovery

Unlike [`../generate-docs`](../generate-docs)'s `run.ts` (which calls `generateDocumentation()`/
`generateUsageReport()` directly, since ENVIRONMENT.md/OWNERSHIP.md need output the persisted
evidence JSON doesn't carry -- see that directory's own README), this generator's only input is
the Lifecycle Model, and the Lifecycle Model already carries every rotation field plus the computed
`rotationStatus` verbatim. `docs/env.evidence.json` is exactly that data, already generated by
`npm run docs`'s `env-cap --evidence` step -- so `build-model.ts` reads it through
`getEvidenceModel()` (a cheap fingerprint-checked read, falling back to a real recompute only on a
genuine mismatch) rather than paying for a second discovery/linking pass.

## Running it

```bash
npm run docs:reports   # generate (chains npm run docs first, so evidence.json is current)
```

Also see `src/runtime/document.ts`'s `VariableDocs` fields (`authenticatorType`/`rotationPeriod`/
`lastRotatedAt`/`rotationTriggerEvents`) in the main package for how to declare rotation data on a
variable in the first place.
